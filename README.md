# Constructor Event Prediction

A reproducible, CPU-only Python 3.11 project that generates synthetic software-delivery event sequences and predicts the next observable event. The implementation follows the registered Constructor Fabric PRD, ADRs, DESIGN, DECOMPOSITION, and FEATURE specifications under `architecture/`.

## Objective and event domain

The project models time-ordered, discrete software architecture and delivery events such as API interface changes, dependency upgrades, compatibility checks, CI failures, fixes, integration-test passes, approvals, deployments, and rollbacks. Every serialized event includes its type and a short human-readable description.

The dataset is generated by a configurable probabilistic state machine with history-dependent modifiers. It is intentionally synthetic: neither its transition probabilities nor the fitted predictors have been validated against real engineering organizations, so the results demonstrate reproducible methodology rather than real-world forecasting performance.

## Architecture

The system has five CPU-only stages:

1. `generate` samples JSONL event sequences from the probabilistic simulator and writes a hash-bound manifest.
2. Complete sequences are split 70/15/15 before observable prefix/next-event examples are created.
3. Three predictors are trained: a global-frequency baseline, a Laplace-smoothed first-order Markov baseline, and multinomial logistic regression over sparse observable-history features.
4. Logistic-regression regularization is selected on validation data only; the held-out test split is used once for reporting.
5. `benchmark` records accuracy, macro-F1, confusion matrices, per-class metrics, sequence-clustered intervals, paired comparisons, error analysis, models, keyed predictions, and hashes. `verify` and the strict artifact verifier check the resulting contracts without retraining.

Constructor Fabric is the project's SDLC, specification, implementation-traceability, and validation system. It is not the simulator or the ML training runtime; Python, NumPy, and scikit-learn execute the data and modeling pipeline.

## Setup

From a clean checkout on Windows PowerShell:

```powershell
py -3.11 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-lock.txt
$env:PYTHONPATH=(Resolve-Path src).Path
.\.venv\Scripts\python.exe -m event_prediction verify --config configs/default.json
.\.venv\Scripts\python.exe -m pytest --cov=event_prediction --cov-branch --cov-report=term-missing --cov-fail-under=90
.\.venv\Scripts\python.exe -m pip check
$studio = (Get-Command constructor-studio -ErrorAction Stop).Source
$env:PYTHONUTF8='1'
& $studio validate --local-only
& $studio spec-coverage --system event-prediction --verbose
```

On POSIX shells:

```sh
python3.11 -m venv .venv
.venv/bin/python -m pip install -r requirements-lock.txt
export PYTHONPATH="$PWD/src"
.venv/bin/python -m event_prediction verify --config configs/default.json
.venv/bin/python -m pytest --cov=event_prediction --cov-branch --cov-report=term-missing --cov-fail-under=90
.venv/bin/python -m pip check
```

The lock contains the complete exact runtime/test environment captured for Python 3.11. The explicit `PYTHONPATH` makes every module command runnable without relying on an editable install. Constructor Studio is needed only for Fabric validation; the Python commands do not depend on it. On Windows systems where long paths are not enabled, clone to a short location such as `C:\src\constructor-event-prediction`; transactional benchmark staging uses descriptive filenames that can otherwise approach the legacy path limit.

## Commands

Generate deterministic JSONL and a manifest:

```powershell
$env:PYTHONPATH='src'
$reviewRun = [guid]::NewGuid().ToString('N')
$datasetPath = Join-Path (Join-Path 'artifacts' "reviewer-generate-$reviewRun") 'dataset.jsonl'
.\.venv\Scripts\python.exe -m event_prediction generate --config configs/default.json --count 200 --seed 42 --output $datasetPath
```

Run a preliminary single-seed benchmark (not the final five-seed benchmark):

```powershell
$reviewRun = [guid]::NewGuid().ToString('N')
$outputDir = Join-Path 'artifacts' "reviewer-benchmark-$reviewRun"
$benchmarkOutput = .\.venv\Scripts\python.exe -m event_prediction benchmark --config configs/default.json --count 200 --seeds 42 --output-dir $outputDir | ConvertFrom-Json
$benchmark = Get-Content -Raw -LiteralPath $benchmarkOutput.result | ConvertFrom-Json
$seedResult = Get-Content -Raw -LiteralPath (Join-Path $outputDir $benchmark.seed_results[0]) | ConvertFrom-Json
$modelPath = Join-Path (Join-Path $outputDir $benchmark.run) $seedResult.model.manifest
```

Predict from a locally produced safe model manifest (JSON plus hash-bound NumPy NPZ arrays loaded with `allow_pickle=False`):

```powershell
.\.venv\Scripts\python.exe -m event_prediction predict --model $modelPath --prefix api_interface_modified compatibility_checked integration_test_passed
```

The equivalent POSIX flow also captures the emitted manifest instead of guessing a run identifier:

```sh
export PYTHONPATH="$PWD/src"
review_run="$(date -u +%Y%m%dT%H%M%S)-$$"
output_dir="artifacts/reviewer-benchmark-$review_run"
benchmark_output="$(.venv/bin/python -m event_prediction benchmark --config configs/default.json --count 200 --seeds 42 --output-dir "$output_dir")"
pointer="$(printf '%s' "$benchmark_output" | .venv/bin/python -c 'import json,sys; print(json.load(sys.stdin)["result"])')"
model_path="$(.venv/bin/python -c 'import json,pathlib,sys; root=pathlib.Path(sys.argv[1]); run=json.loads(pathlib.Path(sys.argv[2]).read_text()); seed=json.loads((root/run["seed_results"][0]).read_text()); print(root/run["run"]/seed["model"]["manifest"])' "$output_dir" "$pointer")"
.venv/bin/python -m event_prediction predict --model "$model_path" --prefix api_interface_modified compatibility_checked integration_test_passed
```

`benchmark` writes each successful attempt under `OUTPUT/runs/` and atomically publishes `OUTPUT/benchmark.json`. The PowerShell GUID (or POSIX timestamp/PID) gives each invocation a fresh output path; keep using the same variable when resolving the pointer, run, seed result, and model. Artifact references in new JSON are output-directory-relative. A run is `COMPLETE` only under the frozen v1 protocol: exactly 10,000 sequences, the exact ordered five seeds, and the exact approved effective-configuration hash, with every seed, split, model, prediction-evidence, aggregate, report, provenance, and hash check succeeding. All other successful runs, including arbitrary five-seed runs, are `PRELIMINARY`; failed attempts leave the last valid pointer byte-for-byte intact and make diagnostic output best-effort.

## Final five-seed benchmark

The frozen benchmark completed once with status `COMPLETE`. It generated 10,000 sequences for each ordered seed `(20261021, 20261022, 20261023, 20261024, 20261025)`. The effective configuration hash is `83b78d453501c33415d8e834ea3f0d46d66aa44278ae2fb1e1f471f1f12e2b51`, and the experiment-profile hash is `75d9435dc2d28a231d3e860abb43689855149a35179c40ab492568d7b11d003d`. The run took 824.300 seconds of wall-clock time.

This is the exact one-time PowerShell invocation used:

```powershell
$env:PYTHONPATH='src'
.\.venv\Scripts\python.exe -m event_prediction benchmark --config configs/default.json --count 10000 --seeds 20261021 20261022 20261023 20261024 20261025 --output-dir artifacts/final
```

`artifacts/final` now contains the immutable published pointer and is protected against overwrite. Do not run that command against the same directory again unless deliberately starting a distinct experiment and following the recovery policy; use a fresh output directory for any later independent run.

| Model | Accuracy, mean ± sample SD | Macro-F1, mean ± sample SD |
|---|---:|---:|
| Global frequency | 0.2040196302 ± 0.0026767226 | 0.0376545498 ± 0.0004102493 |
| First-order Markov | 0.4142268634 ± 0.0033227585 | 0.3004945176 ± 0.0018869513 |
| Logistic regression | 0.4174997578 ± 0.0022595164 | 0.3189212336 ± 0.0030031979 |

Logistic regression exceeded Markov by `0.0032728944 ± 0.0020245367` accuracy and `0.0184267160 ± 0.0045908489` macro-F1 across seeds. All five sequence-clustered 95% confidence intervals for the macro-F1 difference were positive. Accuracy intervals excluded zero for seeds `20261021` and `20261024`, but included zero for `20261022`, `20261023`, and `20261025`. The evidence therefore supports a consistent macro-F1 advantage and a small accuracy advantage that is not uniformly seed-significant. These conclusions apply only to the synthetic domain.

Seeds `20261021` and `20261022` had appeared in earlier preliminary experiments. The ordered five-seed profile, generator configuration, candidate regularization values, metric definitions, and completion contract were frozen before the final run; no setting was selected from final test performance. The logistic model still failed to recover some rare behaviors well: `dependency_upgraded` had zero recall and `ci_failed` recall was approximately 0.004 in the final aggregate. Error-analysis semantic groups can overlap because one incorrect prediction may satisfy more than one category; category counts are therefore non-exclusive and must not be summed as distinct errors.

The strict evidence verifier independently returned `COMPLETE` for all 37 hash-bound artifacts in 242.370 seconds. It can be invoked without retraining or regenerating data:

```powershell
$env:PYTHONPATH='src'
.\.venv\Scripts\python.exe -c "from pathlib import Path; from event_prediction.config import load_config; from event_prediction.benchmark import validate_benchmark_manifest; m=validate_benchmark_manifest(Path('artifacts/final'), load_config(Path('configs/default.json'))); print('ARTIFACT_VERIFY=' + m['status']); print('COUNT=' + str(m['count'])); print('SEEDS=' + ','.join(map(str,m['seeds']))); print('ARTIFACTS=' + str(len(m['artifacts'])))"
```

## Leakage boundary

The simulator's lifecycle context is private and is never serialized. Complete sequences are split before prefix examples are constructed. Feature extraction accepts only an observable `prefix`; target, split, seed, sequence identity, provenance, future events, and simulator state are rejected.

## Limitations

- The event process and text descriptions are hand-designed synthetic abstractions, not measurements of real software teams.
- The simulator shares some of the short-memory structure exploited by the Markov and sparse-history models; conclusions may not transfer to different event processes.
- Rare events have limited support and weak recall even when aggregate macro-F1 improves.
- Five fixed seeds quantify run-to-run variation for this frozen experiment, not uncertainty over real organizations or alternative simulator designs.
- The comparison covers only the approved global-frequency, first-order Markov, and multinomial logistic-regression models.
